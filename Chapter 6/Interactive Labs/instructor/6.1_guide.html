One algorithm, one place: the food bank hours report

Objectives

  • Replace repeated code with one function that captures a general method
  • Use parameters to supply different problem instances to the same algorithm
  • Build a second function on top of the first instead of copying its loop

Requirements

  1. R1 Define total_hours(hours, first_day, last_day) with a docstring. It returns the sum of the hours from first_day through last_day, inclusive (day 1 is hours[0]), and returns 0 when first_day is after last_day. It works on whatever list is passed in, not only HOURS.
  2. R2 total_hours only computes: it does not print and does not ask for input.
  3. R3 Define average_per_day(hours, first_day, last_day). It returns the average hours per day over the range, rounded to 1 decimal place, by calling total_hours. It contains no loop of its own.
  4. R4 In main, the three copied loops are gone: week 1, week 2 and the whole period come from calls to total_hours, and the average line calls average_per_day for days 1 to 14.
  5. R5 main prints the total and the average for the range the coordinator types in, using the two functions.
  6. R6 The test program's results match, including a one-day range, an empty range and a list other than HOURS. (verified by the program output)

Before you code: warm-up and model answers

  1. Press Run on the starter (it uses the program input 3 and 9). Week 1 plus week 2 should equal the two-week total. Does it? Find the line that causes the difference.

    It doesn't: week 1 is 28, week 2 is 23 and the two-week total is 57, so 6 hours are missing. The week 2 loop uses day < 14 instead of day <= 14, so it never adds day 14 (6 hours). The other two copies use <=, so only one copy is wrong.

  2. The coordinator now wants days marked 0 to be counted as 'closed' and skipped. In the starter, how many places would you have to edit? How many after your refactor?

    In the starter, three places, one per copied loop, and I would have to get all three right. After the refactor, only one: the body of total_hours. Every report calls it, so the change reaches all of them.

Solution

volunteer_hours.py
"""volunteer_hours.py - hours report for the Riverside Food Bank's two-week schedule."""

# Hours volunteered on each day of the period. Day 1 is HOURS[0].
HOURS = [3, 5, 0, 4, 6, 2, 8, 4, 4, 5, 0, 7, 3, 6]


def total_hours(hours, first_day, last_day):
    """Return the total of hours from first_day through last_day.
    Days are numbered from 1, so day 1 is hours[0]."""
    total = 0
    day = first_day
    while day <= last_day:
        total += hours[day - 1]
        day += 1
    return total


def average_per_day(hours, first_day, last_day):
    """Return the average hours per day from first_day through last_day,
    rounded to 1 decimal place."""
    days = last_day - first_day + 1
    return round(total_hours(hours, first_day, last_day) / days, 1)


def main():
    """Print the coordinator's report."""
    week1 = total_hours(HOURS, 1, 7)
    week2 = total_hours(HOURS, 8, 14)
    period = total_hours(HOURS, 1, 14)

    print("Week 1:", week1, "hours")
    print("Week 2:", week2, "hours")
    print("Two weeks:", period, "hours")
    print("Average per day:", average_per_day(HOURS, 1, 14))
    print()

    first = int(input("First day of the custom range? "))
    last = int(input("Last day of the custom range? "))
    print("Days", first, "to", last, "total:", total_hours(HOURS, first, last),
          "hours, average:", average_per_day(HOURS, first, last))


if __name__ == "__main__":
    main()

Walkthrough

The three loops in the starter are one algorithm with three problem instances: (1, 7), (8, 14) and (1, 14). A function captures the algorithm once; its parameters receive the instance on each call. The second copy used day < 14, so week 2 lost day 14: exactly the kind of error redundancy invites, because each copy must be right on its own. With one definition, the bug can only live in one place, and fixing it fixes every report. total_hours must use its parameter hours, not the module variable HOURS, or it would ignore the list it is given (the evening-shift test). sum(hours[first_day - 1:last_day]) is an equally correct body. average_per_day reuses total_hours, which is division of labor: one function sums, the other divides, and main only coordinates and prints.

Messages students see when a check fails

C1 · total_hours is defined with three parameters

Write the header def total_hours(hours, first_day, last_day):. The three parameters are the problem instance: which list, and which range of days.

C2 · total_hours has a docstring

Make the first line of the body a docstring in triple quotes, like summation in the reading. Say what it returns and that day 1 is the first item.

C3 · total_hours uses the list it is given

Inside the function, use the parameter (hours), not the module variable HOURS. Otherwise total_hours(evening_shift, 1, 3) would quietly add up the wrong list: the function would solve one problem instance, not a class of problems.

C4 · total_hours returns the total and prints nothing

End with a return statement that hands the total back. Leave printing and input to main: a function that prints can't be reused by average_per_day.

C5 · average_per_day calls total_hours and has no loop

Define average_per_day so it gets the total by calling total_hours(...) with its own three parameters, divides by the number of days, rounds to 1 decimal and returns the result. Writing a fourth summing loop here would bring the redundancy back.

C6 · The average is rounded to 1 decimal

Use round(value, 1) on the average so 4.142857... becomes 4.1.

C7 · main gets the three totals from total_hours

Replace each copied loop in main with one call: total_hours(HOURS, 1, 7) style, a different pair of days each time. main should contain no loop at all.

C8 · main uses both functions for the averages and the custom range

Call average_per_day twice in main: once for days 1 to 14 and once for the coordinator's first and last. Also replace the placeholder total in the last line with a call to total_hours.

Progressive hints

  1. Compare the three loops line by line. What is identical, and what changes? The parts that change become the parameters; everything else becomes the body of total_hours.

  2. Look at summation(lower, upper) in the reading: it walks a counter from the lower bound up to the upper bound. Your version walks day from first_day to last_day and adds hours[day - 1], because day 1 is at index 0.

  3. The number of days in a range is last_day - first_day + 1. average_per_day divides the value total_hours returns by that count, then rounds.

Reflection: questions and model answers

  1. The reading says a function should provide 'a general method with systematic variations'. In your total_hours, what is the general method and what are the variations?

    The general method is the summing algorithm: start at 0, walk the days in a range and add each day's hours. The variations are the problem instances supplied as arguments: which list of hours and which first and last day. One definition solves week 1, week 2, the whole period, a single day and any list.

  2. Why must total_hours use its parameter hours and not the module variable HOURS, even though main always passes HOURS?

    If it used HOURS, the hours parameter would be ignored and the function would only work on one list. The test with the evening shift list would return the food bank's hours instead. Using the parameter keeps the function general, so another program can import it and pass its own data.

  3. main now reads like a summary of the report. Which complexity does each call hide from someone reading main?

    Each call hides the loop, the counter, the running total and the index arithmetic (day - 1). A reader of main sees 'total of week 1' or 'average of days 1 to 14' without having to track three variables per report, so main can be understood in a few seconds.

Extension

Add an optional fourth parameter step to total_hours so the coordinator can total every other day (the reading suggests the same for summation). Then write best_week(hours) that returns 1 or 2, whichever week had more hours, using only calls to total_hours.
