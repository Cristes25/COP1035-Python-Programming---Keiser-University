Whose variable is it? The coffee cart stamp card

Objectives

  • Classify each name in a program as a module variable, a parameter or a temporary variable
  • Explain why assigning to a name inside a function creates a temporary variable instead of changing the module variable
  • Pass data in through parameters and back out through return values instead of changing a module variable

Requirements

  1. R1 add_stamps(count, cups) receives the current count as a parameter and returns the new count. It changes no module variable.
  2. R2 free_drinks(count) returns how many free drinks the stamps are worth (23 stamps earn 2), reading the module variable FREE_DRINK_AT instead of writing 10.
  3. R3 stamps_left(count) returns the stamps that remain after the free drinks are redeemed (23 stamps leave 3), also using FREE_DRINK_AT.
  4. R4 The module variable stamps is gone. main starts its own temporary variable stamps at 0 and updates it with the value add_stamps returns.
  5. R5 No global statements: data moves through parameters and return values only.
  6. R6 The test program's results match: the module has no stamps variable, and two separate cards don't interfere. (verified by the program output)

Before you code: warm-up and model answers

  1. Press Run on the starter. What error does Python report, and on which line? Using the reading's example x = 5 / def f(): x = 10, explain why stamps inside add_stamps is not the module variable.

    UnboundLocalError on the line stamps = stamps + cups: Python says it cannot access the local variable stamps before it has a value. Because the function assigns to stamps, stamps is a temporary variable of add_stamps, like the x inside f in the reading. The right-hand side tries to read that temporary before it has been given a value, so the module variable is never even looked at.

  2. Classify each of these names from the starter as a module variable, a parameter or a temporary variable: FREE_DRINK_AT, add_stamps, cups, count, visits, visit.

    FREE_DRINK_AT and add_stamps are module variables (a function name is a module variable too). cups is a parameter of add_stamps (and a temporary variable in main), count is a parameter of free_drinks and stamps_left, and visits and visit are temporary variables of main.

Solution

loyalty.py
"""loyalty.py - stamp card for the Campus Grind coffee cart.
Every cup earns one stamp; every 10 stamps earn a free drink."""

FREE_DRINK_AT = 10   # module variable used as a constant: functions may read it


def add_stamps(count, cups):
    """Return the number of stamps on a card that had count stamps
    after a visit where cups were bought."""
    return count + cups


def free_drinks(count):
    """Return how many free drinks count stamps are worth."""
    return count // FREE_DRINK_AT


def stamps_left(count):
    """Return the stamps left on the card after the free drinks are redeemed."""
    return count % FREE_DRINK_AT


def main():
    """Record a month of visits and print the card."""
    stamps = 0
    visits = int(input("How many visits this month? "))
    for visit in range(1, visits + 1):
        cups = int(input("Cups on visit " + str(visit) + "? "))
        stamps = add_stamps(stamps, cups)
    print()
    print("Stamps earned:", stamps)
    print("Free drinks:", free_drinks(stamps))
    print("Stamps left on the card:", stamps_left(stamps))


if __name__ == "__main__":
    main()

Walkthrough

Inside add_stamps, the assignment stamps = ... makes stamps a temporary variable of the function, as the reading's x = 10 example shows. Python decides this for the whole body when it compiles the function, so the right-hand side stamps + cups tries to read the temporary before it has a value: UnboundLocalError. Even without the crash, the module variable would not change. The redesign passes the count in as the parameter count and returns the new total; main stores it with stamps = add_stamps(stamps, cups). Now stamps is a temporary variable of main (scope: the body of main; lifetime: one call of main), and count and cups live only for one call of add_stamps. Reading a module variable from a function is fine, which is why free_drinks and stamps_left use FREE_DRINK_AT: if the cart changes the offer to 8, one line changes. count // FREE_DRINK_AT gives the free drinks and count % FREE_DRINK_AT the remainder. Because the functions keep no hidden state, the test program can total two cards side by side.

Messages students see when a check fails

C1 · add_stamps takes the count and the cups

Give add_stamps two parameters: the stamps already on the card first, then the cups bought: def add_stamps(count, cups):. The count arrives through a parameter instead of being read from a module variable.

C2 · add_stamps returns the new count

Return the sum of the two parameters. Don't assign to stamps inside the function: that creates a temporary variable that disappears when the call ends, and the caller never sees the new value.

C3 · free_drinks divides by FREE_DRINK_AT

Return count // FREE_DRINK_AT. Integer division counts whole free drinks, and reading the module variable instead of writing 10 means the offer can change in one place.

C4 · stamps_left uses the remainder

Return count % FREE_DRINK_AT: the stamps that don't make up a full free drink stay on the card.

C5 · The module variable stamps is removed

Delete the line stamps = 0 at the top of the file. The count belongs to one run of main, not to the whole module.

C6 · main keeps the count and stores what add_stamps returns

Start main with stamps = 0, and inside the loop write stamps = add_stamps(stamps, cups). The current count goes in as an argument, and the returned value replaces it.

C7 · No global statements

Remove the global statement. It lets a function change a module variable, but then any function might change it, which is what the reading warns against. Pass the value in and return the result instead.

Reflection: questions and model answers

  1. Give the scope and the lifetime of the parameter count in add_stamps, and of the variable stamps in your main.

    count: its scope is the body of add_stamps, and it exists only while one call of add_stamps runs; each call gets a fresh one. stamps in main: its scope is the body of main below where it is introduced, and it lives for the whole call of main, which is why it can carry the running total across all the visits.

  2. free_drinks reads the module variable FREE_DRINK_AT, yet add_stamps was not allowed to change stamps. Why is reading a module variable acceptable while changing it from a function is risky?

    Reading a value that nobody changes is predictable: every function sees the same 10. If any function can change a module variable, its value depends on which functions ran before, so a bug in one function shows up somewhere else and the functions can't be reused or tested separately. In the test program, two cards would have shared one count.

  3. The test program totals two different cards (card and add_stamps(18, 5)). Why would that be impossible with the starter's design, even if the crash were fixed?

    The starter keeps one count in a single module variable, so every call would add to the same total and the second card would start where the first left off. With parameters and return values, each caller keeps its own count and the function just computes.
